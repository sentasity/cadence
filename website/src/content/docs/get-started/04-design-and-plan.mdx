You have a stub. This lesson grows it into a full **design** you can actually read and approve, then translates the approved design into a **plan**, and shows you exactly how the two differ.

## Design: the stub becomes something you can read

`/c-design` takes your `00-overview.md` stub and turns it into the **design**: the artifact for this stage. By default it's one document of about 1,500 words, in plain English, that you can review fully without opening any code.

<Aside type="note" title="Why design and plan are separate">
A design is for *you*: plain English, decisions explained, reviewable at the level of intent with no code required. A plan is for the *machine*: exact paths and steps, no story. That's why a design never carries schemas, signatures, file lists, or code. Keeping them separate means the thing you approve is the thing you can actually understand.
</Aside>

<Walkthrough title="Design the current-time feature">
  <Fragment slot="step-1-title">Run /c-design</Fragment>
  <Fragment slot="step-1-body">With the stub in place, run `/c-design`. Cadence confirms it will write one design document (for a bigger feature it may offer separate topic documents instead).</Fragment>
  <Fragment slot="step-2-title">Read what it does</Fragment>
  <Fragment slot="step-2-body">The design says why the feature exists, what it does in plain English, and gives concrete examples with the exact output: for the example, `2026-01-15T14:30:00Z`, never local time, never fractions of a second. This is what you read to decide if the design is right.</Fragment>
  <Fragment slot="step-3-title">Read the decisions</Fragment>
  <Fragment slot="step-3-body">One numbered list (`D1`, `D2`, …) records each choice with its rationale: for the example, "use the non-deprecated time API" and "ISO-8601 with a Z suffix, no microseconds". You can see *why*, not just *what*.</Fragment>
  <Fragment slot="step-4-title">Approve it</Fragment>
  <Fragment slot="step-4-body">After a self-review pass, Cadence flips the design to `in-review` and asks you to walk through it. When you're satisfied, you say "approved". That explicit word is the gate. Cadence then tells you to run `/c-plan`.</Fragment>
</Walkthrough>

The finished design for this exact feature ships with Cadence. Open these to see what "done" looks like for the design stage:

  </TabItem>

## Plan: the design becomes exact steps

Once the design is approved, `/c-plan` translates it into a **plan folder**: same name, but written for the machine. A plan is exact paths, exact code, exact commands, and explicit ordering. **No narrative.** That's the visible difference: where the design explains *why*, the plan only states *what and in what order*.

<Aside type="tip" title="One design, one plan">
A design always becomes exactly one plan. If the work is large, the plan splits it into numbered phase files inside that single plan folder. It never spawns separate sibling plans. Cadence also writes a two-way link between the design and the plan so they can't silently drift apart.
</Aside>

<Tabs>
  <TabItem label="Design (for you)">
> Use the current UTC time, formatted ISO-8601 with a `Z` suffix and no microseconds, because it's human-readable and sorts cleanly.
  </TabItem>
  <TabItem label="Plan (for the machine)">
A task with exact `Reads:` / `Touches:` / `Depends:` fields and steps like: write a failing test at a named path, run it and expect failure, implement the function with the full code shown, run the test and expect pass, then commit. No "why": that already lives in the design.
  </TabItem>
</Tabs>

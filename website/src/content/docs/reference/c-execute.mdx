Source of truth: `skills/c-execute/SKILL.md`. For the *why* behind this stage, read the [Execute deep dive](/cadence/execute/).

## Purpose

Drives a draft plan to implemented code: your main session acts as project manager, dispatching a fresh worker per lane (a bundle of tasks), running every change through one reviewer that judges spec and code quality, and auditing the whole thing at the end, so you can trust the result without reading the diff yourself.

## When to use it

Use `/c-execute` when a plan is written and you're ready to build. It is the fourth stage, between plan and audit. Don't use it to deploy or to validate a running system: it stops at implemented code.

## Invocation forms

- `/c-execute <path-to-plan-folder>`: execute the plan.
- `/c-execute --restart <plan-path>`: wipe all checkboxes and start over (never the default; normal re-runs resume where they left off).

## Inputs & preconditions

A plan folder with `00-overview.md` at status `draft` (or `in-progress` to resume), a linked design that is `approved` or later (or, for a `/c-plan --from` plan, its source files), and a clean working tree. It prints the current branch and asks before proceeding if you're on `main`/`master`/`develop`, and (for new-format plans) runs a one-time execution-mode gate: **parallel lanes in worktrees** (recommended) or **inline sequential** (every task implemented by the session itself — no worktrees, no implementer sub-agents; the completion audit still runs as a sub-agent). A concrete `execute.mode` value skips the question. It records the starting commit as `base_sha` on the first run so the audit can compute an exact diff range.

## What it produces

Real code committed to the branch (one commit per task), every plan checkbox flipped to done, and (on a passing completion audit) the plan's status flipped to `implemented`. Plan-file edits are committed once at the end.

## Gates & guarantees

- One reviewer per lane gives two verdicts, spec first and then code quality. The spec decides what gets built; a quality concern about something the plan prescribed is kept for you to decide at the end instead of being dropped. The reviewer fixes Minor findings itself (up to `execute.review_fix_lines` changed lines, inside the lane's files, as a separate commit with the tests re-run); bigger findings go back to the implementer, after which only the fix is re-reviewed, for at most `execute.fix_rounds` rounds. For a task carrying visual citations, the spec verdict takes the design's [visual contract](/cadence/reference/c-design/#the-visual-contract-and-mockups) into its baseline, so a divergence from a named contract value is a spec gap like any other.
- The plan's **Global Constraints** reach every implementer and the reviewer. For a decision plan, the spec verdict checks the plan's decisions (names, files, tests and their assertions, the design's values) and leaves how the code is written to the implementer and the quality verdict; for a full-code plan it still expects an exact match. The style comes from the plan itself, never from config.
- Every implementer report that ran a step command quotes its real test output (the failing run before the change, the passing run after), and the reviewer checks it against what the plan said to expect. When a test misbehaves, the implementer tests one hypothesis at a time and stops after three failed attempts with an account of what it tried. When the plan itself is wrong it stops right away, and that reaches you as a plan question.
- Where the plan says nothing, the reviewer judges the code by what a reasonable user would expect: a clear violation gets fixed, and an unclear case goes on an end-of-run list. The list (rulings, held lanes, reviewer items, and the branch review's non-Critical findings) lives in the plan overview. Nothing a reviewer declines is dropped, and nothing the plan prescribed is added.
- Parallel work runs in lanes: ready tasks bundled in plan order up to `execute.bundle_words` words of task text, each in its own worktree, scheduled by the tasks' dependencies, with a guard that serializes any two lanes touching the same files. `execute.max_parallel` caps running implementers, so the next independent lane starts while the previous one is in review. Every task commit carries a `Cadence-Task:` trailer, so a lane interrupted mid-way resumes at its first uncommitted task instead of starting over. Inline mode trades that machinery (and independent review) for a single sequential session; the completion audit is unchanged in both modes.
- Merging a lane back (merge-on-land) acquires the shared merge lock, so cross-session merges into the same working branch (for example, a concurrent `/c-worktree` merge) serialize instead of colliding (gated by `worktree.merge_lock`).
- A completion audit must pass, and no end-of-run item may be left undecided, before the status can flip to `implemented`. The audit's branch review reads the design and the whole branch on the most capable model; only a Critical finding blocks.
- Drift never stops the run: the PM makes a ruling (the best-fitting reading, a task expanded or split, an out-of-scope entry), records it in the plan's Review decisions table, and continues. A lane that can't finish is held with its work preserved while independent lanes keep going. At the end you answer one grouped question covering every ruling, held lane, and review item, each with a recommendation. It stops mid-run only before a destructive, security-sensitive, or outside-the-worktree action.
- It never auto-deploys, never amends commits, never skips commit hooks, and never reads the whole repo on every worker dispatch.
